# GHOSTBOARD OS — benchmarks

## Status: not yet measured on target hardware

**The table below is empty on purpose.** GHOSTBOARD OS was built in a headless
cloud container — no Intel N100, no NVMe, no 800 × 480 panel, no GPU. Boot time,
resting RAM and NVMe throughput are properties of the real deck, and inventing
them here would make this file worse than useless.

Fill it by running this on the deck, after a reboot into the GHOSTBOARD session:

```bash
ghost-bench --markdown /opt/ghostboard-os/BENCHMARKS.md
```

`ghost-bench` rewrites only the generated block below; the prose around it
survives. Anything it cannot measure it reports as `unavailable` — it never
estimates.

## Targets

| Measurement | Target | Why |
| --- | ---: | --- |
| Boot to usable desktop | **< 20 s** | Wall clock from power-on to a taskbar you can click. Not "systemd finished". |
| RAM at rest, desktop loaded | **< 900 MB** | `MemTotal - MemAvailable`. Page cache does not count — it is handed back on demand. |
| CPU at rest | **< 3 %** | The test that proves nothing is running for nothing. |
| Terminal launch | **< 700 ms** | Click to mapped window. This is what NVMe is for. |
| NVMe sequential read | **> 500 MB/s** | `dd iflag=direct`, bypassing page cache. Without `O_DIRECT` you measure RAM. |
| GPU clients after boot | **none** | The boot animation must have destroyed its WebGL context. |

## Known costs to watch on the deck

Three things are expected to show up in the first real measurement. They are
called out here so they are not mistaken for surprises.

1. **Chromium startup for the splash.** The animation itself is 1.4 s, but
   Chromium has to start and parse 365 KB of three.js first — measured at
   ~350 ms under software rendering, likely less on the iGPU. Budget roughly
   2.5–3 s of the 20 s for the whole splash. If that is too much,
   `boot.enabled = false` removes it entirely.
2. **The compositor stays on.** `use_compositing = true` in `xfwm4.xml` is
   required for the taskbar's mica translucency. It costs little on an N100 iGPU
   and nothing while idle, unlike an animation. If resting CPU comes in over
   target, this is the first thing to test with.
3. **`systemd-analyze blame` after every change.** `95-perf-tuning` disables a
   specific list — ModemManager, Bluetooth, CUPS, Avahi, PackageKit, the apt
   daily timers, `NetworkManager-wait-online`. Each is a deliberate choice for
   this deck, not a copied list. Re-check blame after any package install: a
   dependency can quietly re-enable one.

## Reading the output

```bash
ghost-bench                  # table, verdicts, slowest units, GPU clients
ghost-bench --json           # raw, for scripting
ghost-bench --quick          # skips disk and app-launch timing
ghost-bench --markdown FILE  # rewrites the generated block above
```

Exit code is `1` if any target fails, so it can gate a build.

`boot_to_desktop_s` needs one login to exist: an autostart entry calls
`ghost-bench --mark-ready` when the desktop is up, and that timestamp is what
the metric is measured against. Before the first GHOSTBOARD session it reports
`unavailable` rather than falling back to the systemd number, which measures
something else.
